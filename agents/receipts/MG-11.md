## Step 0 - how CUDA arrives

### The probe

A throwaway crate outside both repos, `E:\CraftML\work\.codex-tmp\mg11-probe` (`ort` 2.0.0-rc.14 with `cuda` + `preload-dylibs`, plus `ndarray` and `flate2`), run with `cargo run --offline`. It loads the real `birefnet_lite.onnx` from the golden store, turns ONNX Runtime profiling on, asks for the CUDA execution provider, runs one 1x3x1024x1024 job, and counts the `provider` field of every node event in the profiling JSON. It also asks `nvidia-smi` for free VRAM before and after. Nothing from the probe is in the repo; the numbers below are reproducible from it.

### 1. Which `ort` gives CAIM the CUDA provider

`ort = "2.0.0-rc.14"` is already the dependency (MG-04), with its default features: `std`, `ndarray`, `tracing`, `download-binaries`, `tls-native`, `copy-dylibs`, `api-31` (= ONNX Runtime 1.31). Two features are added, and nothing else:

- **`cuda`** - compiles the CUDA EP registration into `ort` (`ort::ep::CUDA`) and tells `ort-sys` to fetch the CUDA-flavoured prebuilt ONNX Runtime.
- **`preload-dylibs`** - brings `ort::ep::cuda::preload_dylibs(cuda_dir, cudnn_dir)` (`ort-2.0.0-rc.14/src/ep/cuda.rs:359`), which `LoadLibrary`s the NVIDIA DLLs from a directory CAIM owns before the EP looks for them. This is the "load the CUDA provider's libraries at run time" the prompt asks for: CAIM points the runtime at its own download folder instead of touching `PATH`, and a machine that never asks for CUDA never opens those files. It pulls one crate, `libloading` 0.9.0 (ISC).

**Rejected: `load-dynamic`.** It would make CAIM open a *whole* `onnxruntime.dll` at run time instead of linking one at build time, which is the smallest possible installer - but the pyke prebuilt distributions `ort-sys` downloads do not ship `onnxruntime.dll` (they ship a static `onnxruntime.lib` plus the provider DLLs), so CAIM would have to find and fetch Microsoft's own runtime build, own its version, and re-do MG-04's CPU path. That is a bigger risk than the installer growth, and it is not what amendment 18 asks for. Recorded because it is the option a reviewer will ask about.

### 2. What the build actually does with `cuda` on

`ort-sys` 2.0.0-rc.14, `build/download/dist.tsv`, ONNX Runtime 1.31, `x86_64-pc-windows-msvc`:

| feature set | dist bytes | SHA-256 |
|---|---|---|
| `directml` (what CAIM builds today) | 32,457,673 | `f99aaef23f12986abb05924c944d8433521263ad756b462df762a5a982c98405` |
| `cuda13,tensorrt,nvrtx,directml` (what `cuda` selects) | 89,325,556 | `3a0095001aa415a0cb7a56f847bd85764fccd8f20147abedc18994893a49776d` |

`ort-sys` resolves `cuda` to `cuda13` on Windows (`build/download/resolve.rs`); `ORT_CUDA_VERSION=12|13` overrides it. Both dists come from `https://cdn.pyke.io/0/pyke:ort-rs/ms@1.31.0/...` and are content-addressed into `ORT_CACHE_DIR`.

Two things about linking, both verified by reading `ort-sys/build/static_link/mod.rs` and by building the probe on a PC with no CUDA toolkit:

- **No CUDA import library is ever needed at link time.** The CUDA EP ships as a separate provider DLL, and the `optional_link_lib` list (`static_link/mod.rs:332-385`) deliberately leaves cuda out. The only Windows link libs added are `shell32` (`:44`) and, because every pyke Windows dist is built with DirectML compiled in, `dxguid`, `DXCORE`, `DXGI`, `D3D12`, `DirectML` (`:50-54`). That DirectML *link* is already true of MG-04's build; it is not a device choice, and D10 (no DirectML in M2) is about the EP we register, which stays CPU/CUDA only.
- **`copy-dylibs` (a default feature) copies the dist's DLLs next to the executable at build time.** With `cuda`, the probe's output folder gained `onnxruntime_providers_cuda.dll` 93,791,744, `DirectML.dll` 18,527,776, `onnxruntime_providers_tensorrt.dll` 768,512, `onnxruntime_providers_nv_tensorrt_rtx.dll` 722,944 and `onnxruntime_providers_shared.dll` 10,752 - about 114 MB beside `caim.exe`, against ~51 MB today. Those DLLs are never loaded unless a CUDA session is created, so a CPU-only machine still runs, but the installer does grow by roughly that much. That is the honest cost of `ort`'s static-link default, and it is the reason the prompt's "prefer run-time loading" is only partly reachable - see the `load-dynamic` note above.

### 3. The finding that changes the design: ONNX Runtime does not tell you CUDA ran

With the CUDA EP asked for and **no NVIDIA runtime DLLs on the machine at all**, every "is CUDA working" check passes:

- `ort::ep::CUDA::is_available()` -> `Ok(true)`;
- `Session::builder().with_execution_providers([ep::CUDA::default().build()])` -> `Ok`;
- `commit_from_file` -> a session; `run` -> an output; no error anywhere.

The profiling JSON is the only thing that says the truth: **3,930 node events, all 3,930 with `"provider": "CPUExecutionProvider"`**, in the CUDA-labelled run and in the CPU-labelled run. Free VRAM was unchanged before and after (991 MiB both times). So a CAIM that believed `is_available()` or "the session built" would report `"device": "cuda"` for a job that ran on the CPU - amendment 18's done-when item 6 ("every result says what was requested, what ran, and why it fell back") would be a lie on this machine, which is the single most likely way to get this task wrong.

Two consequences, both built:

1. **Before** a CUDA session is created, CAIM preloads the NVIDIA DLLs itself (`preload_dylibs`) from its own download folder. A DLL that will not load is a real, early `backend_unavailable` - the only honest way to know the runtime is missing.
2. **After** the first CUDA run, CAIM reads the run's own placement: ONNX Runtime profiling is turned on for CUDA sessions, and the node events are counted. Zero events on `CUDAExecutionProvider` means the EP silently fell back inside the runtime, which amendment 18 calls `backend_init_failed` ("present but would not start"), and the job re-runs on the CPU. `execution_failed` stays for a CUDA run that starts on the GPU and then fails.

### 4. Where the CUDA/cuDNN libraries come from

Nothing needs an NVIDIA account, a login, or a click-through page. NVIDIA publishes exact-version redist archives on a plain CDN and, next to each one, a machine-readable index with sizes and SHA-256:

- `https://developer.download.nvidia.com/compute/cuda/redist/redistrib_13.4.3.json`
- `https://developer.download.nvidia.com/compute/cudnn/redist/redistrib_9.27.0.json`
- archive URL = `https://developer.download.nvidia.com/compute/<cuda|cudnn>/redist/` + the `relative_path` in that index.

The four archives CAIM pins (re-read from those two indexes on 2026-10-18, values below are what NVIDIA serves today; the CUDA 13.4.3 index is the one matching the `cuda13` dist `ort` builds against, and cuDNN 9.27.0 is a `cuda13` variant):

| `libcublas` | 13.8.0.4 | `libcublas/windows-x86_64/libcublas-windows-x86_64-13.8.0.4-archive.zip` | 422,415,931 | `0974318e9861a61cb9091cf7de8d4c2880e9787fe311cb4bcbd08865663c5f43` |
| `libcufft` | 12.4.0.43 | `libcufft/windows-x86_64/libcufft-windows-x86_64-12.4.0.43-archive.zip` | 159,602,693 | `69d0ad8dc3a1be66f01a748a8206d0ceaafa56939474663fbe790dc3e91d2009` |

**1,915,559,656 bytes downloaded (~1.9 GB), ~1.4 GB on disk** - inside amendment 18's "about 1-2 GB". CAIM does not extract a whole archive: it reads the zip directory, takes the pinned entry names, and inflates those, so a tampered archive cannot make it write an unexpected path. The DLL names are the ones `ort` itself preloads (`ort/src/ep/cuda.rs:332` and `:337`): CUDA `cudart64_13.dll`, `cublasLt64_13.dll`, `cublas64_13.dll`, `cufft64_12.dll`; cuDNN `cudnn64_9.dll`, `cudnn_graph64_9.dll`, `cudnn_ops64_9.dll`, `cudnn_heuristic64_9.dll`, `cudnn_adv64_9.dll`, `cudnn_cnn64_9.dll`, `cudnn_engines_precompiled64_9.dll`, `cudnn_engines_runtime_compiled64_9.dll`. Every entry in these archives is plain deflate, so an inflater is all that is needed - no zip crate, no archive crate.

They download only when the device setting asks for CUDA (or Auto on a machine with an NVIDIA card), they go through MG-02's existing store path (size + SHA-256 + `verified.json` + the acknowledgment record), and they are re-checked the same way. CAIM's own `.part` resume (MG-12) is reused.

### 5. Licence

`cuda_cudart`, `libcublas` and `libcufft` are redist components of the **CUDA Toolkit** (`license = "CUDA Toolkit"` in that index); `cudnn` is under the **cuDNN SLA**. Both let NVIDIA's redist components be redistributed and used with an application, and both are EULAs rather than permissive licences - which is why CAIM does not silently fetch them: the install prints the two licence names and what it is about to download, and needs an explicit acknowledgment, the same gate MG-02 built for a model's licence (and the same one D11 uses for a flagged model). Amendment 17's "new libraries must be permissive" rule is about code CAIM links, and the two crates this task adds are permissive (next section); the NVIDIA binaries are data CAIM downloads on request, under their own terms, with the user's click.

## What was built

18 files changed (+2,948 / -203). Two are new - `src/device.rs` (864 lines) and `src/cuda.rs` (934 lines) - and the code that already existed changed in eleven more (`lama.rs`, `birefnet.rs`, `job.rs`, `cli.rs`, `main.rs`, `server.rs`, `activity.rs`, `lib.rs`, `Cargo.toml`, and the `golden` and `activity_log` tests). Nothing outside `cuda.rs` says "CUDA" or "VRAM" (amendment 18), and there is no `ComputeBackend` trait.

- **`src/device.rs` (new).** The one resolver. `Device` {`Cpu`, `Cuda`}; `Setting` {`Auto`, `Cuda`, `Cpu`} with `parse` and `token`; `Reason`, whose `token()` can only ever say amendment 18's five words; `Manifest`, a thin read-only view of a catalog entry (`id`, `memory_mib`, `backends`) plus `cpu_only` for a pipeline built straight from a path; `Accelerator` and `Machine::probe`; `Decision` {requested, chain, reason, device_name, note}; `Resolver::resolve` and `resolve_lazy`.
- **The order `resolve` walks**, because the cheap and honest answers come first: a `cpu` setting is a CPU job with no fallback to report; a manifest that does not mark `cuda` `supported` (or `experimental` when someone asks) is `unsupported_model`; a machine with no card is `backend_unavailable`; a card without the downloaded libraries is `backend_unavailable` with a note naming `caim cuda install --accept-note`; free VRAM below the model's `memory_mib` is `insufficient_memory`; otherwise the chain is `[cuda, cpu]`. `resolve_lazy` means the vendor's tool never runs for `--device cpu` or for a model with no tested CUDA build, so a machine with no GPU never starts `nvidia-smi`.
- **A reason and a sentence only land in the result when the setting was `cuda`.** `auto` that ends on the CPU asked for "the best available", got it, and reports `fallback_reason: null` - amendment 18's "null when the requested backend ran". `--device cuda` that ends on the CPU always names one of the five.
- **`run_on_chain`** (with `Attempt`, `ChainOutcome`, `Runner`, `LoadStage`) is the only code that tries a device. It loads a session, runs, and on a mid-run failure retries once on the next device; a job that was deleted stays a cancellation rather than becoming a fallback; a chain that cannot run the job at all fails once with one plain sentence (`NO_DEVICE`). `bounded_diagnostics` flattens the vendor's text and cuts it at 600 characters (`MAX_DIAGNOSTICS`) so `diagnostics` can never grow a response.
- **`src/cuda.rs` (new).** Everything CUDA: `PROBE`/`PROBE_ARGS` with a 5 s timeout (`PROBE_TIMEOUT`) and a 50 ms poll; `components()`, which turns the four pinned NVIDIA archives from step 0 into catalog-shaped `Model`s (`TASK_LIBRARIES = "cuda_libraries"`) so MG-02's store and MG-12's resume do the hashing, the `.part` resume and the acknowledgment for them; `wanted()` for the DLL names `ort` itself preloads; `CUDA_DIR = "cuda"` beside the models folder, overridable with `CRAFT_AI_CUDA`, and `library_dir` = `<root>\bin`; `install`/`install_all` behind the license acknowledgment; `status_lines`; `cards()` and `accelerators()` (biggest free card wins, `ready` = every wanted file present); `preload`, once per folder per process, remembering failures in `PRELOADED` so a broken folder is not retried per job; `job_gate`, one GPU job at a time (`GPU_JOB`); `Placement`/`verdict`, which counts the node events whose `provider` is `CUDAExecutionProvider` (`placed_nodes`); `CHOSEN_CARD`, which remembers the card the probe picked so `register(builder)` can bind ONNX Runtime to that same card; and `register(builder)` itself.
- **`extract` is CAIM's own zip reader** (EOCD, central directory, one deflate per member through `flate2`). It reads the archive's directory, takes only the entries `wanted()` named, and checks each member's CRC and size before writing. A tampered archive therefore cannot make CAIM write a path it did not ask for. Nine tests cover the CRC mismatch, the length mismatch, a non-archive, a missing member, stored vs deflated, and "leave a library that is already right alone".
- **The runners (`lama.rs`, `birefnet.rs`).** `load_ort_session(path, device)` adds `cuda::preload`, profiling and `cuda::register` **only** when the device is `Cuda`; the CPU builder is byte for byte what MG-04 built. `OrtSession::run` takes the GPU gate, then reads the placement back: nodes that did not land on the card become `Attempt::Failed { BackendInitFailed }`, and an inference error becomes `ExecutionFailed`. The session cache is keyed by device (`Mutex<Option<(Device, Box<dyn Session>)>>`), so a fallback keeps the session that worked instead of reloading. `run_fill_on` / `run_mask_on` take a `Decision`; `run_fill` / `run_mask` stay for callers that have no resolver.
- **`job.rs`.** `Backend::Real` carries the `device::Setting` for the start, and `decision_for` resolves **per job** from the model's own manifest, because free VRAM changes between jobs. `Backend::note()` is now a `String` and names the device that was asked for rather than promising the CPU.
- **`server.rs`, `cli.rs`, `main.rs`.** `ServeOptions.device`; `caim serve --device auto|cuda|cpu` (also `--device=cuda`, case-insensitive, and refused anywhere but `serve`); `caim cuda status`; `caim cuda install [--accept-note]` (`--accept-note` is refused on commands that do not download anything).
- **`protocol.rs` is deliberately unchanged.** `DEVICES = ["cpu"]` (`crates/caim/src/protocol.rs:32`, pinned by `crates/caim/tests/protocol.rs:65`) is what can run *now*: the NVIDIA libraries are not installed here and both manifests say `cuda = "untested"`. Listing `cuda` in health before either is true would be the kind of promise amendment 18 is written against. The flip belongs with the manifest, not with the wire format.

## CI round 1: two tests that quietly assumed Windows

CAIM's CI runs the same suite on ubuntu, on windows and on MSRV 1.95. The first run on this branch (`39175556320`) failed two library tests on ubuntu and on msrv, and both were our bug rather than a runner problem.

- `ort_only_asks_for_names_caim_unpacks` asserted that every name in ONNX Runtime's own `CUDA_DYLIBS` and `CUDNN_DYLIBS` is a name CAIM unpacks. Those lists are compiled per platform, so on Linux the assertion runs against `libcudart.so.13` and friends, while every archive CAIM pins is NVIDIA's `windows-x86_64` redist set. The invariant is a Windows one, so it is now `#[cfg(windows)]` and says so.
- `the_cuda_folder_is_a_sibling_of_the_models_folder` built its fixture out of `C:\Users\Erik\...` literals. On Unix such a literal is a single path component with no parent, so `store_root_in` answered `cuda` and the assert compared that to the literal. The fixture is now built with `PathBuf` from `std::env::temp_dir()`, which has a parent on every platform. The rule under test - a `cuda` folder beside the models folder, `CRAFT_AI_CUDA` winning over it - did not change.

The first failure also pointed at something real in the product, so it is fixed there and not only in the test. The four pinned archives are Windows-only, but nothing said so: on Linux `caim cuda install --accept-note` would have fetched 1.9 GB of `.dll` files into a folder `dlopen` cannot use, `caim cuda status` would have listed them as missing, and `is_ready` would have answered `true` for a catalog with nothing in it. Now:

- `cuda::supported_here()` is the one place that names the covered platform (`cfg!(windows)`), and `cuda::unpinned_sentence()` is the words it uses;
- `components()` is empty off Windows, so there is nothing to fetch and nothing to list;
- `is_ready` needs a non-empty catalog, so an empty one is never "ready";
- `install` refuses with the platform named, instead of reporting "ready ... 0 files from 0 archives";
- `accelerators()` hands the resolver that sentence as the card's note, so a Linux box holding a 4090 gets `backend_unavailable` plus "Craft AI Manager has no CUDA library download pinned for linux yet" rather than an instruction to run a command that cannot help;
- `status_lines` says the same thing.

Two tests pin the new rule on both platforms: `the_pinned_catalog_exists_only_on_the_platform_it_is_pinned_for`, and `a_folder_full_of_the_pinned_names_is_ready_only_where_they_are_pinned` - a folder holding all nineteen names is ready only where those names are pinned. NVIDIA's index does carry a `linux-x86_64` set; pinning it is a task with its own versions, hashes and evidence, and MG-11 has no Linux card to test it on.

Gates after the fix: `cargo fmt --all -- --check` 0, `cargo clippy --offline --all-targets -- -D warnings` 0, `cargo test --offline` **376 passed / 0 failed / 7 ignored** (329 library plus 47 integration).

## Independent review round 1: five findings, five fixes

Codex-cloud reviewed `cbf624e` and `60cca53` and left five inline findings (4309189758, 4309189764, 4309189770, 4309189771, 4309210697). All five are real. All five are fixed in `crates/caim/src/cuda.rs`, `device.rs`, `lama.rs`, `birefnet.rs` and `job.rs`.

- **P1 - the placement mark was the wrong string.** `CUDA_NODE_MARK` was `"CUDA Execution Provider"`. ONNX Runtime's identifier is `CUDAExecutionProvider`, no spaces - which is exactly what step 0's probe recorded (`"provider": "CPUExecutionProvider"`), so the spaced spelling matched nothing in any profile. Every CUDA run would have come back `NotPlaced`, been thrown away, and re-run on the CPU with `backend_init_failed`: the check that exists to stop a false `cuda` result would have been a machine that always answers no. The constant is now the runtime's own name, and `the_mark_is_the_runtimes_own_name` pins it to `<ort::ep::CUDA as ort::ep::ExecutionProvider>::NAME` so the two cannot drift again. The counting moved into `placed_nodes`, which `a_profile_counts_the_nodes_that_ran_on_the_card` tests against profile-shaped text - the profile itself only exists on a machine that has run a card session, so this is as close as the invariant gets to a test without a card.
- **P1 - the Linux CUDA archives.** The second half of the CI finding above; already fixed in `60cca53`.
- **P2 - the memory gate charged a warm session twice.** `free_mib` is measured *after* the pipeline's cached CUDA session has allocated its model, so on a card where the first load leaves less than `memory_mib` free, job 1 runs on CUDA and every job after it falls back to the CPU and replaces the warm session. `device::Accelerator` now carries `resident`: the probe always leaves it false, and `crate::job` sets it from the pipeline that owns the session (`holds_card_session()` on both pipelines). The gate then applies only to a model that still has to be loaded. `a_model_already_sitting_on_the_card_is_not_charged_twice` covers both directions - a model that is *not* resident still has to fit in what is free.
- **P2 - the provider was not bound to the card the probe chose.** With two cards, `accelerators()` picks the one with the most free memory while `ort::ep::CUDA::default()` uses device 0, so CAIM could name one card and run on the other. `Card` now carries its index in the probe's order, `accelerators()` records the card it chose in `CHOSEN_CARD`, and `register()` passes it with `with_device_id`. `the_probe_lists_cards_in_the_order_the_runtime_numbers_them` pins the numbering and shows the two cards disagreeing.
- **P2 - the pinned catalog is x86_64-only.** `supported_here()` was `cfg!(windows)`; on a 32-bit or ARM64 Windows build it would have fetched 1.9 GB of `windows-x86_64` DLLs that the process cannot load, and `is_ready` would have believed them. It is now `cfg!(all(target_os = "windows", target_arch = "x86_64"))`, so those builds get the unpinned-platform sentence like every other one.

## Independent review round 2: two findings about *which* card

Codex-cloud re-reviewed the round-1 commits and left two P2s (4309271942 at `crates/caim/src/job.rs:128`, 4309271950 at `crates/caim/src/cuda.rs:401`). Both are real, and they are the same mistake seen twice: CAIM measures one card and then runs on whichever card ONNX Runtime happens to number 0.

- **P2 - residency was charged to "a CUDA session", not to a card.** `Machine::mark_resident` took only a device, so a warm session on card 0 excused the memory gate for card 1, and `holds_card_session()` could only answer "yes, there is one". `device::Accelerator` and `device::Decision` now carry `card: Option<i32>`; `mark_resident(device, card)` matches on both and does nothing for `None`; both runner traits gained a `Session::card()` default method; `OrtSession` records the card it was built for (`cuda::chosen_card()` when the CUDA provider was registered, `None` otherwise); `holds_card_session()` became `session_card() -> Option<i32>` on both pipelines and `job::decision_for` passes it. `run_fill_on` and `run_mask_on` now drop a cached CUDA session whose card is not the card the resolver has just chosen before running on it, so a job can never be reported against a card nobody measured; a warm CPU session that survived a fallback is left alone.
- **P2 - `nvidia-smi` row order is not CUDA ordinal.** `accelerators()` chose the row with the most free memory and bound the provider to that row's index, but CUDA numbers cards by `CUDA_VISIBLE_DEVICES` and `CUDA_DEVICE_ORDER`, not by the order the vendor tool prints them. `Card` now keeps `probe_index` (what `nvidia-smi` printed) apart from `ordinal` (what the runtime uses), and the probe asks for `uuid` and `pci.bus_id` as well. `ordinals()` numbers the cards only where the mapping is provable: a single card whose probe index is 0; `CUDA_DEVICE_ORDER=PCI_BUS_ID` with a bus id for every card; or `CUDA_VISIBLE_DEVICES` set, where the list *is* the order - by index or by UUID, case-insensitively, an empty value meaning no cards and an entry that matches nothing meaning none of them can be numbered. Anything else, above all two cards with nothing set, leaves them unnumbered and `chosen_among()` refuses to choose rather than bind a job to a card nobody can name. `accelerators()` then reports the card with `ready: false` and a note naming what is missing, and `status_lines()` prints `device <n>` or "device number unknown". `chosen_card()` is now the one number the runners and the provider both read.

New tests: `one_card_is_the_card_onnx_runtime_numbers_zero`, `two_cards_with_no_order_set_are_not_numbered_at_all`, `pci_bus_id_order_numbers_the_cards_by_their_slot` and `a_visible_devices_list_is_the_order_the_runtime_numbers_in` in `crates/caim/src/cuda.rs`; `a_session_on_another_card_does_not_excuse_this_one` in `crates/caim/src/device.rs`; `a_warm_session_on_another_card_is_not_reused` in `crates/caim/src/lama.rs`. The probe-parse tests were rebuilt around `ONE_CARD` and `TWO_CARDS` fixtures that carry the new columns.
