## Step 0 - how CUDA arrives

Written before any product code, as the prompt asks. Everything in this section was measured on this machine, not read off a README.

### The probe

A throwaway crate outside both repos, `E:\CraftML\work\.codex-tmp\mg11-probe` (`ort` 2.0.0-rc.14 with `cuda` + `preload-dylibs`, plus `ndarray` and `flate2`), run with `cargo run --offline`. It loads the real `birefnet_lite.onnx` from the golden store, turns ONNX Runtime profiling on, asks for the CUDA execution provider, runs one 1x3x1024x1024 job, and counts the `provider` field of every node event in the profiling JSON. It also asks `nvidia-smi` for free VRAM before and after. Nothing from the probe is in the repo; the numbers below are reproducible from it.

### 1. Which `ort` gives CAIM the CUDA provider

`ort = "2.0.0-rc.14"` is already the dependency (MG-04), with its default features: `std`, `ndarray`, `tracing`, `download-binaries`, `tls-native`, `copy-dylibs`, `api-31` (= ONNX Runtime 1.31). Two features are added, and nothing else:

- **`cuda`** - compiles the CUDA EP registration into `ort` (`ort::ep::CUDA`) and tells `ort-sys` to fetch the CUDA-flavoured prebuilt ONNX Runtime.
- **`preload-dylibs`** - brings `ort::ep::cuda::preload_dylibs(cuda_dir, cudnn_dir)` (`ort-2.0.0-rc.14/src/ep/cuda.rs:359`), which `LoadLibrary`s the NVIDIA DLLs from a directory CAIM owns before the EP looks for them. This is the "load the CUDA provider's libraries at run time" the prompt asks for: CAIM points the runtime at its own download folder instead of touching `PATH`, and a machine that never asks for CUDA never opens those files. It pulls one crate, `libloading` 0.9.0 (ISC).

**Rejected: `load-dynamic`.** It would make CAIM open a *whole* `onnxruntime.dll` at run time instead of linking one at build time, which is the smallest possible installer - but the pyke prebuilt distributions `ort-sys` downloads do not ship `onnxruntime.dll` (they ship a static `onnxruntime.lib` plus the provider DLLs), so CAIM would have to find and fetch Microsoft's own runtime build, own its version, and re-do MG-04's CPU path. That is a bigger risk than the installer growth, and it is not what amendment 18 asks for. Recorded because it is the option a reviewer will ask about.

### 2. What the build actually does with `cuda` on

`ort-sys` 2.0.0-rc.14, `build/download/dist.tsv`, ONNX Runtime 1.31, `x86_64-pc-windows-msvc`:

| feature set | dist bytes | SHA-256 |
|---|---|---|
| `directml` (what CAIM builds today) | 32,457,673 | `f99aaef23f12986abb05924c944d8433521263ad756b462df762a5a982c98405` |
| `cuda13,tensorrt,nvrtx,directml` (what `cuda` selects) | 89,325,556 | `3a0095001aa415a0cb7a56f847bd85764fccd8f20147abedc18994893a49776d` |

`ort-sys` resolves `cuda` to `cuda13` on Windows (`build/download/resolve.rs`); `ORT_CUDA_VERSION=12|13` overrides it. Both dists come from `https://cdn.pyke.io/0/pyke:ort-rs/ms@1.31.0/...` and are content-addressed into `ORT_CACHE_DIR`.

Two things about linking, both verified by reading `ort-sys/build/static_link/mod.rs` and by building the probe on a PC with no CUDA toolkit:

- **No CUDA import library is ever needed at link time.** The CUDA EP ships as a separate provider DLL, and the `optional_link_lib` list (`static_link/mod.rs:332-385`) deliberately leaves cuda out. The only Windows link libs added are `shell32` (`:44`) and, because every pyke Windows dist is built with DirectML compiled in, `dxguid`, `DXCORE`, `DXGI`, `D3D12`, `DirectML` (`:50-54`). That DirectML *link* is already true of MG-04's build; it is not a device choice, and D10 (no DirectML in M2) is about the EP we register, which stays CPU/CUDA only.
- **`copy-dylibs` (a default feature) copies the dist's DLLs next to the executable at build time.** With `cuda`, the probe's output folder gained `onnxruntime_providers_cuda.dll` 93,791,744, `DirectML.dll` 18,527,776, `onnxruntime_providers_tensorrt.dll` 768,512, `onnxruntime_providers_nv_tensorrt_rtx.dll` 722,944 and `onnxruntime_providers_shared.dll` 10,752 - about 114 MB beside `caim.exe`, against ~51 MB today. Those DLLs are never loaded unless a CUDA session is created, so a CPU-only machine still runs, but the installer does grow by roughly that much. That is the honest cost of `ort`'s static-link default, and it is the reason the prompt's "prefer run-time loading" is only partly reachable - see the `load-dynamic` note above.

### 3. The finding that changes the design: ONNX Runtime does not tell you CUDA ran

With the CUDA EP asked for and **no NVIDIA runtime DLLs on the machine at all**, every "is CUDA working" check passes:

- `ort::ep::CUDA::is_available()` -> `Ok(true)`;
- `Session::builder().with_execution_providers([ep::CUDA::default().build()])` -> `Ok`;
- `commit_from_file` -> a session; `run` -> an output; no error anywhere.

The profiling JSON is the only thing that says the truth: **3,930 node events, all 3,930 with `"provider": "CPUExecutionProvider"`**, in the CUDA-labelled run and in the CPU-labelled run. Free VRAM was unchanged before and after (991 MiB both times). So a CAIM that believed `is_available()` or "the session built" would report `"device": "cuda"` for a job that ran on the CPU - amendment 18's done-when item 6 ("every result says what was requested, what ran, and why it fell back") would be a lie on this machine, which is the single most likely way to get this task wrong.

Two consequences, both built:

1. **Before** a CUDA session is created, CAIM preloads the NVIDIA DLLs itself (`preload_dylibs`) from its own download folder. A DLL that will not load is a real, early `backend_unavailable` - the only honest way to know the runtime is missing.
2. **After** the first CUDA run, CAIM reads the run's own placement: ONNX Runtime profiling is turned on for CUDA sessions, and the node events are counted. Zero events on `CUDAExecutionProvider` means the EP silently fell back inside the runtime, which amendment 18 calls `backend_init_failed` ("present but would not start"), and the job re-runs on the CPU. `execution_failed` stays for a CUDA run that starts on the GPU and then fails.

### 4. Where the CUDA/cuDNN libraries come from

Nothing needs an NVIDIA account, a login, or a click-through page. NVIDIA publishes exact-version redist archives on a plain CDN and, next to each one, a machine-readable index with sizes and SHA-256:

- `https://developer.download.nvidia.com/compute/cuda/redist/redistrib_13.4.3.json`
- `https://developer.download.nvidia.com/compute/cudnn/redist/redistrib_9.27.0.json`
- archive URL = `https://developer.download.nvidia.com/compute/<cuda|cudnn>/redist/` + the `relative_path` in that index.

The four archives CAIM pins (re-read from those two indexes on 2026-10-18, values below are what NVIDIA serves today; the CUDA 13.4.3 index is the one matching the `cuda13` dist `ort` builds against, and cuDNN 9.27.0 is a `cuda13` variant):

**1,915,559,656 bytes downloaded (~1.9 GB), ~1.4 GB on disk** - inside amendment 18's "about 1-2 GB". CAIM does not extract a whole archive: it reads the zip directory, takes the pinned entry names, and inflates those, so a tampered archive cannot make it write an unexpected path. The DLL names are the ones `ort` itself preloads (`ort/src/ep/cuda.rs:332` and `:337`): CUDA `cudart64_13.dll`, `cublasLt64_13.dll`, `cublas64_13.dll`, `cufft64_12.dll`; cuDNN `cudnn64_9.dll`, `cudnn_graph64_9.dll`, `cudnn_ops64_9.dll`, `cudnn_heuristic64_9.dll`, `cudnn_adv64_9.dll`, `cudnn_cnn64_9.dll`, `cudnn_engines_precompiled64_9.dll`, `cudnn_engines_runtime_compiled64_9.dll`. Every entry in these archives is plain deflate, so an inflater is all that is needed - no zip crate, no archive crate.

They download only when the device setting asks for CUDA (or Auto on a machine with an NVIDIA card), they go through MG-02's existing store path (size + SHA-256 + `verified.json` + the acknowledgment record), and they are re-checked the same way. CAIM's own `.part` resume (MG-12) is reused.

### 5. Licence

`cuda_cudart`, `libcublas` and `libcufft` are redist components of the **CUDA Toolkit** (`license = "CUDA Toolkit"` in that index); `cudnn` is under the **cuDNN SLA**. Both let NVIDIA's redist components be redistributed and used with an application, and both are EULAs rather than permissive licences - which is why CAIM does not silently fetch them: the install prints the two licence names and what it is about to download, and needs an explicit acknowledgment, the same gate MG-02 built for a model's licence (and the same one D11 uses for a flagged model). Amendment 17's "new libraries must be permissive" rule is about code CAIM links, and the two crates this task adds are permissive (next section); the NVIDIA binaries are data CAIM downloads on request, under their own terms, with the user's click.
