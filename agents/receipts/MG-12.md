## What changed

### 1. Restart-safe resume (`crates/caim/src/fetch.rs`, `crates/caim/src/store.rs`)

- `store::PartMeta` (`crates/caim/src/store.rs:143`) - `url`, `revision`, `sha256`, `bytes` - written by `store::write_part_meta` (`crates/caim/src/store.rs:156`) the same atomic way `endpoint.json` is written: a temp name of its own next to the target, then a rename. `store::read_part_meta` (`crates/caim/src/store.rs:179`) reads at most 64 KiB and returns `None` for anything that is not a whole JSON object, so a note cut in half by a crash is simply no note.
- `store::part_meta_file` / `store::is_part_meta_name` (`crates/caim/src/store.rs:97`, `crates/caim/src/store.rs:104`) sit beside the existing `part_file` / `is_part_name`, so the note follows the same naming rules as the `.part` it describes.
- `Fetch::open_range(url, offset)` (`crates/caim/src/fetch.rs:80`) is a new method with a default that ignores the offset and calls `open` - a fetch that knows nothing about ranges behaves like a server that does. `HttpFetch::open_range` (`crates/caim/src/fetch.rs:128`) sends `Range: bytes=<offset>-` and reads the answer through the pure `resume_answer(url, offset, status)` (`crates/caim/src/fetch.rs:145`): `206` is `Answer::Partial`, `200` is `Answer::Full`, anything else is the named error `resume_status_error`. `Stream` carries the answer (`crates/caim/src/fetch.rs:51`), so the caller knows whether the bytes on disk are still the front of the file.
- `fetch_into_place` (`crates/caim/src/fetch.rs:250`) takes a `Resume` (`crates/caim/src/fetch.rs:225`) rather than a flag: `NoLock` for the pre-existing race test that deliberately bypasses the lock, `FreshLock` when this install created the lock file itself, and `TakenOver` when it took the lock over from an install that looks dead. `download()` asks the lock which one it is (`InstallLock::resume`, `crates/caim/src/fetch.rs:589`). With resume on, `adopt_part` (`crates/caim/src/fetch.rs:418`) looks for an abandoned pair, renames it under this install's own tag, and re-hashes it into a `Sha256` so the running hash continues where the last run stopped. `progress(offset, size)` fires once before the first byte of the new request, which is the resumed offset the prompt asks for.
- The note is written when the part is opened and then every `META_EVERY` = 8 MiB (`crates/caim/src/fetch.rs:161`, `crates/caim/src/fetch.rs:339`). A note that cannot be written is a sentence on stderr and costs only the bytes after that point.
- `200` on a range request: the pair is deleted, the hasher restarted, offset back to zero (`crates/caim/src/fetch.rs:286`). Any other status, or a request that cannot be opened at all: the pair stays and the sentence ends "... N bytes are on disk, so running the same command again picks the download up." (`crates/caim/src/fetch.rs:279`).
- A note that does not describe this exact file - another url, revision or SHA-256, zero bytes, more bytes than the catalog's size - deletes both and starts from zero (`crates/caim/src/fetch.rs:440`). A `.part` *shorter* than its note is missing bytes the note vouches for, so that pair goes too; a `.part` *longer* than its note is the normal case after a kill between checkpoints, so `truncate_to` (`crates/caim/src/fetch.rs:521`) cuts the unrecorded tail off and the recorded prefix is what resumes (`crates/caim/src/fetch.rs:451`).
- A download that stops for a reason that is not the bytes' fault - a read error mid-stream, or a stream that ends short of the catalog size - keeps the pair, writes a final note with the true count, and says the same sentence (`keep_what_arrived`, `crates/caim/src/fetch.rs:536`). Nothing is kept when nothing arrived. Everything that *is* the bytes' fault - more bytes than the catalog, a wrong final SHA-256, a failed write or rename - deletes both (`abandon_pair`, `crates/caim/src/fetch.rs:692`), which is the amendment's hash-mismatch rule and keeps the old short-download behaviour of throwing the bytes away out of it.
- `remove_dead_parts` (`crates/caim/src/fetch.rs:394`) changed with it: a stale `.part` that still has its note is a download the next install can pick up, so it stays; a `.part` with no note and a note with no `.part` are both junk and go.
- `Outcome::Downloaded` gained `resumed_from` (`crates/caim/src/fetch.rs:171`) and `caim models install` prints it: "... 208044816 bytes, 134217728 of them already on disk" (`crates/caim/src/models.rs:111`).

`APP_NAME` / `APP_VERSION` / `AppFile` (`crates/caim/src/endpoint.rs:30`), `app_path_for` (`crates/caim/src/endpoint.rs:120`) - the file next to the endpoint file - and `write_app` (`crates/caim/src/endpoint.rs:127`), which writes `{"version": 1, "exe": "<absolute path>"}` with the same temp-then-rename as `endpoint.json`. `Server::start_with_stop` writes it just after the endpoint file (`crates/caim/src/server.rs:184`), so `serve` and `open` both write it on every start. ### 4. Activity log (`crates/caim/src/activity.rs`, `crates/caim/src/job.rs`)

`Record` (`crates/caim/src/activity.rs:45`) is the amendment's nine fields; `version`, `device_requested` and `fallback_reason` are `null` today because MG-10 and MG-11 are what will fill them, and writing them as `null` keeps the file's shape fixed for whoever reads it. `time` is a `YYYY-MM-DDThh:mm:ssZ` stamp made from `SystemTime::now()` with no chrono (the civil-date arithmetic is `civil_from_days`, `crates/caim/src/activity.rs:171`, tested against known UTC seconds). `append` (`crates/caim/src/activity.rs:77`) writes one line, then `trim` (`crates/caim/src/activity.rs:96`) rewrites the file only past `TRIM_AT` = 1,100 lines, keeping the newest `MAX_LINES` = 1,000; a line over 8 KiB is not something CAIM wrote and is dropped rather than kept, and the rewrite reads at most the last 8 MiB by seeking, so the log cannot grow the read into a full-file copy.

`Runner` holds the path (`set_activity_log`, `crates/caim/src/job.rs:236`), which `Server::start_with_stop` sets next to the endpoint file it is about to write (`crates/caim/src/server.rs:174`); a run with no endpoint file has no log. One line per finished job, written where the job finishes: `finish` (`crates/caim/src/job.rs:486`), `cancel` (`crates/caim/src/job.rs:307`) and `request_stop` (`crates/caim/src/job.rs:391`). A job cancelled by `DELETE` already has its line by the time `finish` runs, and `finish` skips a job whose state is already final, so a cancelled job has exactly one line. `log_activity` (`crates/caim/src/job.rs:573`) swallows the error into a sentence on stderr: the job's own result is decided before the log is touched.

## Why the part files carry a tag

Amendment 18 names `<file>.part` and `<file>.part.json`. CAIM writes `<file>.<tag>.part` and `<file>.<tag>.part.json`, where `<tag>` is this install's 16 hex characters (`install_tag`, `crates/caim/src/fetch.rs:382`). The reason is the invariant MG-02 built and its tests still enforce: each install creates its own `.part` with `create_new` and renames into place only the bytes it hashed itself, so two installs of one model can never put a wrong file under the verified name. A single shared `<file>.part` would break that the moment two installs ran - they would write over each other's bytes and each other's note, and each would rename bytes it had not hashed. Keeping the tag costs one folder scan in `adopt_part`, which renames an abandoned pair under the new install's tag before it continues it. The README says this out loud in the same place the C6 rule is described.

`adopt_part` refuses a pair unless **both** halves are older than `LOCK_STALE` (two minutes). A `.part` that was written to a minute ago may belong to an install that is still running - the lock is supposed to keep that from happening, and the lock-takeover test proves a second install can still get there - so a fresh pair is left alone and the install starts from zero.

## Review round 1 (one P1 and two P2 from Codex on `517c40b`)

**P1 - a `.part` longer than its note threw the whole download away** (`crates/caim/src/fetch.rs:451`). The check was `written != Some(note.bytes)`, so any part with more bytes than the note counted was deleted with its note. That is the normal shape after a kill between the 8 MiB checkpoints - the file keeps going while the note lags - so most abrupt interruptions lost every byte and started the 200 MB again. A longer part is now cut back to the checkpoint (`truncate_to`, `crates/caim/src/fetch.rs:521`) and the recorded prefix is what resumes; only a part *shorter* than its note, missing bytes the note claims were written, is rejected. `a_part_longer_than_its_note_resumes_from_the_last_checkpoint` and `a_part_shorter_than_its_note_starts_the_download_over` cover both sides.

**P2 - the next run made you wait two minutes for bytes it had just saved** (`crates/caim/src/fetch.rs:433`). `keep_what_arrived` writes a fresh pair and the `InstallLock` is then released cleanly, so the rerun the sentence promises - "running the same command again picks the download up" - skipped the pair as too young and fetched the whole model again, and the abandoned pair sat on disk after the new install succeeded. The staleness rule is only needed while another installer might own the pair, so `fetch_into_place` takes a `Resume` (`crates/caim/src/fetch.rs:225`) instead of a flag and `InstallLock` remembers how it was acquired: `create_new` succeeding means no other installer exists (`FreshLock`, adopt a pair of any age), while a `claim_stale` takeover means the install that left the lock might only be stalled (`TakenOver`, keep the both-halves-old rule). `a_half_file_someone_is_writing_to_is_not_picked_up` was reworked into the takeover path - it leaves a stale lock file behind - and `a_pair_the_last_try_left_behind_is_adopted_without_waiting` covers the fresh one. `a_download_that_stops_short_keeps_what_arrived` and `a_refused_range_keeps_the_bytes_for_the_next_try` no longer age the pair before rerunning, which is the user-visible part of the fix.

**P2 - two jobs finishing at the same moment could split a log line or drop one** (`crates/caim/src/activity.rs:77`). Connection threads cancel and finish different jobs concurrently, and the JSON and the newline were two `write_all` calls followed by an unsynchronized read-and-rewrite trim: interleaved writes made one invalid line, and two trims could each rewrite from their own snapshot and lose the other caller's record. The whole append and trim now runs under a process-wide `LOG_LOCK` (`crates/caim/src/activity.rs:41`) and each record goes out as one buffer. `jobs_finishing_at_the_same_time_each_keep_one_whole_line` has four threads finish five jobs each and asks for 20 whole JSON lines. Writers in another process are still not serialized - one manager owns this file - which the code and the gap below now say out loud.

**A guard run then caught a flaky test of mine, not a Codex finding.** The third pass of `agents/guards.txt` failed on `crates/caim/tests/activity_log.rs:18`: `activity.jsonl` was not there yet. `finish` (`crates/caim/src/job.rs:550`) drops the queue lock before writing the line, on purpose - the disk must not hold up the queue - so a job's new state is public a moment before its log line lands. The log is a convenience, so the reader waits: `wait_for_lines` polls until the file has the lines it expects, and the three tests that read straight after a state change use it. Twelve reruns of that file pass; the full guard set is below.

## Known gaps and follow-ups

- The note is flushed every 8 MiB, so a killed download loses at most the last 8 MiB of progress. Flushing per chunk would cost a rewrite of the note per chunk for a 200 MB file; the amendment asks for "at least every 8 MiB".
- A resumed download trusts the server to send the same bytes from the offset it was given. The final SHA-256 is what proves it: a server that answers `206` with different bytes fails the hash and both files go.
- `activity.jsonl` has no reader yet. MG-13's window is where "last job" gets shown, and MG-10/MG-11 turn the three `null` fields into values.
- `caim open` starts a headless server; MG-13 gives it the window. PhotoCraft's button (PC-10) is what reads `app.json`.
- The activity log is written by the manager, so a run with `CRAFT_AI_ENDPOINT` unset still logs - into the default data folder - and a run with no data folder at all logs nowhere.
- `LOG_LOCK` serializes the threads of one manager. Two managers pointed at the same folder could still interleave; the endpoint file and the token already assume one manager per data folder, and MG-13's window is where the log gets read.
- A finished job's state is public a moment before its `activity.jsonl` line lands, because the queue lock is dropped before the write. Anything reading the log - MG-13's "last job" - has to look for the newest line rather than assume it is there.
