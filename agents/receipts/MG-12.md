## What changed

### 1. Restart-safe resume (`crates/caim/src/fetch.rs`, `crates/caim/src/store.rs`)

- `store::PartMeta` (`crates/caim/src/store.rs:143`) - `url`, `revision`, `sha256`, `bytes` - written by `store::write_part_meta` (`crates/caim/src/store.rs:156`) the same atomic way `endpoint.json` is written: a temp name of its own next to the target, then a rename. `store::read_part_meta` (`crates/caim/src/store.rs:179`) reads at most 64 KiB and returns `None` for anything that is not a whole JSON object, so a note cut in half by a crash is simply no note.
- `store::part_meta_file` / `store::is_part_meta_name` (`crates/caim/src/store.rs:97`, `crates/caim/src/store.rs:104`) sit beside the existing `part_file` / `is_part_name`, so the note follows the same naming rules as the `.part` it describes.
- `Fetch::open_range(url, offset)` (`crates/caim/src/fetch.rs:80`) is a new method with a default that ignores the offset and calls `open` - a fetch that knows nothing about ranges behaves like a server that does. `HttpFetch::open_range` (`crates/caim/src/fetch.rs:128`) sends `Range: bytes=<offset>-` and reads the answer through the pure `resume_answer(url, offset, status)` (`crates/caim/src/fetch.rs:145`): `206` is `Answer::Partial`, `200` is `Answer::Full`, anything else is the named error `resume_status_error`. `Stream` carries the answer (`crates/caim/src/fetch.rs:51`), so the caller knows whether the bytes on disk are still the front of the file.
- `fetch_into_place` (`crates/caim/src/fetch.rs:250`) takes a `Resume` (`crates/caim/src/fetch.rs:225`) rather than a flag: `NoLock` for the pre-existing race test that deliberately bypasses the lock, `FreshLock` when this install created the lock file itself, and `TakenOver` when it took the lock over from an install that looks dead. `download()` asks the lock which one it is (`InstallLock::resume`, `crates/caim/src/fetch.rs:651`). With resume on, `adopt_part` (`crates/caim/src/fetch.rs:433`) looks for an abandoned pair, renames it under this install's own tag, and re-hashes it into a `Sha256` so the running hash continues where the last run stopped. `progress(offset, size)` fires once before the first byte of the new request, which is the resumed offset the prompt asks for.
- The note is written when the part is opened and then every `META_EVERY` = 8 MiB (`crates/caim/src/fetch.rs:161`, `crates/caim/src/fetch.rs:343`). A note that cannot be written is a sentence on stderr and costs only the bytes after that point.
- `200` on a range request: the pair is deleted, the hasher restarted, offset back to zero (`crates/caim/src/fetch.rs:291`). Any other status, or a request that cannot be opened at all: the pair stays and the sentence ends "... N bytes are on disk, so running the same command again picks the download up." (`crates/caim/src/fetch.rs:283`).
- A note that does not describe this exact file - another url, revision or SHA-256, zero bytes, more bytes than the catalog's size - deletes both and starts from zero (`crates/caim/src/fetch.rs:455`). A `.part` *shorter* than its note is missing bytes the note vouches for, so that pair goes too; a `.part` *longer* than its note is the normal case after a kill between checkpoints, so `truncate_to` (`crates/caim/src/fetch.rs:583`) cuts the unrecorded tail off and the recorded prefix is what resumes (`crates/caim/src/fetch.rs:466`).
- A download that stops for a reason that is not the bytes' fault - a read error mid-stream, or a stream that ends short of the catalog size - keeps the pair, writes a final note with the true count, and says the same sentence (`keep_what_arrived`, `crates/caim/src/fetch.rs:598`). Nothing is kept when nothing arrived. Everything that *is* the bytes' fault - more bytes than the catalog, a wrong final SHA-256, a failed write or rename - deletes both (`abandon_pair`, `crates/caim/src/fetch.rs:754`), which is the amendment's hash-mismatch rule and keeps the old short-download behaviour of throwing the bytes away out of it.
- `remove_dead_parts` (`crates/caim/src/fetch.rs:408`) changed with it: a stale `.part` that still has its note is a download the next install can pick up, so it stays; a `.part` with no note and a note with no `.part` are both junk and go.
- `Outcome::Downloaded` gained `resumed_from` (`crates/caim/src/fetch.rs:171`) and `caim models install` prints it: "... 208044816 bytes, 134217728 of them already on disk" (`crates/caim/src/models.rs:111`).

## Why the part files carry a tag

Amendment 18 names `<file>.part` and `<file>.part.json`. CAIM writes `<file>.<tag>.part` and `<file>.<tag>.part.json`, where `<tag>` is this install's 16 hex characters (`install_tag`, `crates/caim/src/fetch.rs:396`). The reason is the invariant MG-02 built and its tests still enforce: each install creates its own `.part` with `create_new` and renames into place only the bytes it hashed itself, so two installs of one model can never put a wrong file under the verified name. A single shared `<file>.part` would break that the moment two installs ran - they would write over each other's bytes and each other's note, and each would rename bytes it had not hashed. Keeping the tag costs one folder scan in `adopt_part`, which renames an abandoned pair under the new install's tag before it continues it. The README says this out loud in the same place the C6 rule is described.

`adopt_part` adopts a pair only when it can be sure nobody is writing one. An install that created the lock file itself has no other installer, so it takes the pair its own last run left however young it is (`Resume::FreshLock`, `crates/caim/src/fetch.rs:448`). An install that took the lock over from a lock that looks dead insists **both** halves are older than `LOCK_STALE` (two minutes), because the install that left them may only be stalled - the lock is meant to keep a second install out, and the lock-takeover test proves one can still get there. A takeover also never writes into the bytes it found: it copies the recorded prefix into a `.part` of its own (`copy_prefix_and_hash`, `crates/caim/src/fetch.rs:510`), because the stalled owner may still hold the old file open and a rename would leave this install verifying bytes somebody else is still appending to.

## Review round 1 (one P1 and two P2 from Codex on `517c40b`)

**P1 - a `.part` longer than its note threw the whole download away** (`crates/caim/src/fetch.rs:466`). The check was `written != Some(note.bytes)`, so any part with more bytes than the note counted was deleted with its note. That is the normal shape after a kill between the 8 MiB checkpoints - the file keeps going while the note lags - so most abrupt interruptions lost every byte and started the 200 MB again. A longer part is now cut back to the checkpoint (`truncate_to`, `crates/caim/src/fetch.rs:583`) and the recorded prefix is what resumes; only a part *shorter* than its note, missing bytes the note claims were written, is rejected. `a_part_longer_than_its_note_resumes_from_the_last_checkpoint` and `a_part_shorter_than_its_note_starts_the_download_over` cover both sides.

**P2 - the next run made you wait two minutes for bytes it had just saved** (`crates/caim/src/fetch.rs:448`). `keep_what_arrived` writes a fresh pair and the `InstallLock` is then released cleanly, so the rerun the sentence promises - "running the same command again picks the download up" - skipped the pair as too young and fetched the whole model again, and the abandoned pair sat on disk after the new install succeeded. The staleness rule is only needed while another installer might own the pair, so `fetch_into_place` takes a `Resume` (`crates/caim/src/fetch.rs:225`) instead of a flag and `InstallLock` remembers how it was acquired: `create_new` succeeding means no other installer exists (`FreshLock`, adopt a pair of any age), while a `claim_stale` takeover means the install that left the lock might only be stalled (`TakenOver`, keep the both-halves-old rule). `a_half_file_someone_is_writing_to_is_not_picked_up` was reworked into the takeover path - it leaves a stale lock file behind - and `a_pair_the_last_try_left_behind_is_adopted_without_waiting` covers the fresh one. `a_download_that_stops_short_keeps_what_arrived` and `a_refused_range_keeps_the_bytes_for_the_next_try` no longer age the pair before rerunning, which is the user-visible part of the fix.

**P2 - two jobs finishing at the same moment could split a log line or drop one** (`crates/caim/src/activity.rs:77`). Connection threads cancel and finish different jobs concurrently, and the JSON and the newline were two `write_all` calls followed by an unsynchronized read-and-rewrite trim: interleaved writes made one invalid line, and two trims could each rewrite from their own snapshot and lose the other caller's record. The whole append and trim now runs under a process-wide `LOG_LOCK` (`crates/caim/src/activity.rs:41`) and each record goes out as one buffer. `jobs_finishing_at_the_same_time_each_keep_one_whole_line` has four threads finish five jobs each and asks for 20 whole JSON lines. Writers in another process are still not serialized - one manager owns this file - which the code and the gap below now say out loud.

**A guard run then caught a flaky test of mine, not a Codex finding.** The third pass of `agents/guards.txt` failed on `crates/caim/tests/activity_log.rs:18`: `activity.jsonl` was not there yet. `finish` (`crates/caim/src/job.rs:550`) drops the queue lock before writing the line, on purpose - the disk must not hold up the queue - so a job's new state is public a moment before its log line lands. The log is a convenience, so the reader waits: `wait_for_lines` polls until the file has the lines it expects, and the three tests that read straight after a state change use it. Twelve reruns of that file pass; the full guard set is below.

## Review round 2 (one P1 and two P2 from Codex on `9cd3309`)

**P1 - a takeover could verify a file another install was still writing** (`crates/caim/src/fetch.rs:470`). `adopt_part` renamed the abandoned `.part` under this install's tag. On Unix a rename moves the same inode, so an install blocked in a network read for longer than `LOCK_STALE` - lock, part and note all stale, the file still open - went on appending to the very file the takeover then hashed and renamed into place, and `verified.json` could describe bytes the other process had changed. A takeover now copies the recorded prefix into a `.part` of its own, hashing it in the same pass (`copy_prefix_and_hash`, `crates/caim/src/fetch.rs:510`), and only then deletes the old pair: the bytes before the note's count were written at least `LOCK_STALE` ago, so the copy is a stable snapshot, and the file this install renames is one nobody else holds open. A lock this install created itself still renames, because then no other installer exists. `a_takeover_copies_the_bytes_it_resumes_from_rather_than_writing_into_them` fails against the old code and passes against the new.

**P2 - a part whose note already counted the whole file asked the server for a range that could only be refused** (`crates/caim/src/fetch.rs:270`). A note written at the final checkpoint, or a stream that ended exactly at the catalog size, left a complete `.part`; the next install still asked for `Range: bytes=<size>-`, a compliant server answers 416, the pair was kept, and every retry repeated the same request forever. Those bytes are now hashed and put in place where they are, and the server is not contacted at all; both the streamed and the already-whole path end in one `finalize_part` (`crates/caim/src/fetch.rs:371`). `a_part_whose_note_counts_the_whole_file_is_finished_without_asking_the_server` asserts `asked()` is empty.

**P2 - a health answer split across reads made `caim open` start a second manager** (`crates/caim/src/endpoint.rs:235`). One `read` can legally return a fragment of the status line, so `HTTP/1.1 2` read as "nothing is answering": `caim open` would bind the port and overwrite the live manager's `endpoint.json`. The check now reads until the status line ends, the peer hangs up, or the 250 ms budget is spent, and only then looks for the 200. `a_health_answer_that_arrives_in_pieces_is_still_one_manager` answers in two writes with a pause between them.

## Known gaps and follow-ups

- The note is flushed every 8 MiB, so a killed download loses at most the last 8 MiB of progress. Flushing per chunk would cost a rewrite of the note per chunk for a 200 MB file; the amendment asks for "at least every 8 MiB".
- A resumed download trusts the server to send the same bytes from the offset it was given. The final SHA-256 is what proves it: a server that answers `206` with different bytes fails the hash and both files go.
- `activity.jsonl` has no reader yet. MG-13's window is where "last job" gets shown, and MG-10/MG-11 turn the three `null` fields into values.
- `caim open` starts a headless server; MG-13 gives it the window. PhotoCraft's button (PC-10) is what reads `app.json`.
- The activity log is written by the manager, so a run with `CRAFT_AI_ENDPOINT` unset still logs - into the default data folder - and a run with no data folder at all logs nowhere.
- `LOG_LOCK` serializes the threads of one manager. Two managers pointed at the same folder could still interleave; the endpoint file and the token already assume one manager per data folder, and MG-13's window is where the log gets read.
- A finished job's state is public a moment before its `activity.jsonl` line lands, because the queue lock is dropped before the write. Anything reading the log - MG-13's "last job" - has to look for the newest line rather than assume it is there.
- A lock takeover reads the recorded prefix twice - once to copy it, once to continue the hash - so a takeover of a 200 MB download costs one extra pass over the bytes already on disk. It is the rare path (the common one is the same command run again, which renames), and it is what keeps a stalled installer from writing into a file this install is verifying.
