## Known gaps and follow-ups

- The lock's stale rule (2 minutes without a touch) means a download whose server stalls for more than 2 minutes can
  be taken over by a second install (see Follow-up: both then write their own `.part`, so this is safe).
- A 413 body (over 1 GiB) is drained only for `drain_timeout` (5 s). A client still writing a multi-GiB body after
  that may still see a reset. This is bounded on purpose.
- PhotoCraft's side of X1/X2 (BF-02: blend by coverage once, and read a reply after a failed write) is not in this repo.

## Follow-up (review of `2710da5`)

The reviewer approved BF-01 and asked for one fix before merge: **C6 still had a race.** If a stale lock existed and two
installs started together, both could `remove_file` it and both believe they held the lock. B could then rename A's
half-written `.part` and record it as verified. The `still_ours()`-then-rename and the check-then-remove in `Drop` were
also two-step races.

What changed (`crates/caim/src/fetch.rs`, `crates/caim/src/store.rs`):

- **Each install now has its own part file**, `<file>.<16 hex>.part`, from `store::part_file(root, model, tag)`, created
  with `create_new`. `fetch_into_place` renames only that file, so the bytes renamed are always the bytes that install
  hashed. Correctness no longer rests on the lock; the lock only keeps two installs from downloading the same 200 MB
  at once. `abandon` deletes only the install's own part file. The `still_ours()` check before the rename is gone.
- **Taking over a stale lock** (`claim_stale`): the lock is renamed to `<file>.lock.<nonce>.stale` first, and only one
  renamer can win. The moved file is checked again: if it is not stale, a fresh lock arrived in between and is put
  back. Only then is it deleted.
- **Releasing the lock** (`Drop`): it is renamed aside to `<file>.lock.<nonce>.release`, deleted there if it holds this
  install's nonce, and otherwise put back.
- **Files left by dead runs:** `.part` files that match the model (including the old untagged `<file>.part`) and that
  nobody has written to for `LOCK_STALE` (2 min) are removed by the install that holds the lock. A live install
  writes every chunk, so its file is never that old. A recently written `.part` is left alone. If a download stalls
  for more than 2 min and then resumes, its rename finds no file and it fails cleanly. On Windows, an open file is
  not deleted.
- README: the download paragraph describes the per-install part file and the rename-to-claim rule. A new sentence
  says slow clients are now limited (at most 5 s per slot for the head), but a local process that keeps reconnecting
  16 sockets can still cause 503s, which is accepted on loopback.

Tests (in `fetch.rs`):

- `two_installs_racing_over_a_stale_lock_never_leave_a_wrong_file_marked_verified` (new, 6 rounds): a stale lock, then
  two installs released together by a `Barrier`, one served the right bytes and one the wrong ones. Any verified file
  holds the right bytes, and no `.part`, lock, `.stale` or `.release` file is left.
- `two_downloads_that_both_think_they_hold_the_lock_cannot_install_the_wrong_bytes` (new, 6 rounds): two
  `fetch_into_place` calls with no lock at all, which is the worst case of a takeover gone wrong. Neither ever installs
  the wrong bytes.
- `part_files_left_by_dead_runs_are_cleared_and_a_live_one_is_not` replaces `a_part_file_left_by_a_dead_run_is_replaced`.
  `store::the_part_file_and_the_records_sit_next_to_the_model_file` now covers the tagged name and `is_part_name`.
- Honest note: the reviewer's interleaving needs sub-millisecond timing, so no test was run that shows it failing on
  `2710da5`. The two new tests check the new rule (each install renames only its own hashed bytes) directly and under
  a real race.
