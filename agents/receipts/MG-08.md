## What changed

- **`crates/caim/Cargo.toml`** - one new dependency, `ctrlc = { version = "3.5.2", features = ["termination"] }`.
  Licence MIT / Apache-2.0, so it is inside the MG-07 `deny.toml` allow list. `termination` is what makes
  the handler see SIGTERM and SIGHUP as well as SIGINT; on Windows the same handler covers Ctrl+C,
  Ctrl+Break, a console close and logoff. `Cargo.lock` gains 7 packages: ctrlc 3.5.2, nix 0.31.3 and
  cfg_aliases 0.2.2 (Unix), block2 0.6.2, dispatch2 0.3.1, objc2 0.6.5, objc2-encode 4.1.0 (Apple). On
  Windows ctrlc uses `windows-sys` 0.61.2, which the tree already had, so nothing new is added there.
- **`crates/caim/src/server.rs`** - `StopHandle` (`crates/caim/src/server.rs:280`) over a private
  `StopState` (`crates/caim/src/server.rs:263`), `Server::stop_handle()`
  (`crates/caim/src/server.rs:238`), and `Server::start_with_stop()`
  (`crates/caim/src/server.rs:150`). `StopHandle::press()` (`crates/caim/src/server.rs:307`) is the
  shutdown path: the first press sets the stop flag and calls `Runner::request_stop()`, which is
  exactly what Enter does today; a press after that returns true, meaning "leave now", and `forced()`
  remembers it. `Server::shutdown()` is unchanged, so the endpoint file still goes away only when it
  holds this start's token (`endpoint::remove` asks `is_ours` first).
- **`crates/caim/src/main.rs`** - `watch_signals()` (`crates/caim/src/main.rs:210`) installs
  `ctrlc::set_handler`: the first press calls `press()`, a second press calls
  `std::process::exit(EXIT_FAILED)` from the signal thread, which is exit code 1. If the handler cannot
  be installed the server still runs, prints the sentence, and stops on Enter as before. Since round 2
  `serve` calls it *before* `Server::start`, not after it. The terminal line now reads "press Enter or
  Ctrl+C to stop cleanly. A second Ctrl+C leaves at once."
- **`README.md`** - "Stopping it" rewritten: Enter and Ctrl+C are the same clean stop; a second Ctrl+C
  ends at once with exit code 1 and may leave the file behind.
- **`agents/guards.txt`** - one new line, `MG-08 | craft-ai-manager | cargo test`.

| presses | gap | exit code | `endpoint.json` after |
|---|---|---|---|
| 1 | - | 0 | gone |
| 2 | 0 ms | 1 | still there - the forced exit beat the cleanup |
| 2 | 30 ms | 0 | gone - the clean stop had already finished |
| 2 | 250 ms | 0 | gone |

One Ctrl+C is the clean stop with exit 0. A second one that arrives while that stop is still running
leaves at once with 1, and the stale file is the same harmless case the README already describes: a
client gets a refused connection, and the next start replaces it.

Re-run after the merge with `3aca441`, same helper, same four rows: exit 0 / 1 / 0 / 0 and the file
gone / still there / gone / gone.

Re-run on the round-2 tree: 1 press exit 0 file gone; 2 presses 0 ms exit 1 file still there; 2 at
250 ms exit 0 file gone (twice). The 30 ms row is a coin flip - three runs gave 0, 1, 0 - because a
second press that lands exactly as the clean stop finishes is the boundary case by design.

The round-2 window itself (a press before the endpoint file exists) is under ~25 ms on this machine,
too short to hit reliably from PowerShell: at 25, 50, 100 and 200 ms after the start the file is
already there and every press gave exit 0 with the file gone. The unit test above is what covers the
press-before-start case.

## Review round 2 (one P2 from Codex on `312e50d2`)

Codex's second review found one P2: `watch_signals` ran *after* `Server::start` had written
`endpoint.json` and after `serve` had printed its "listening" lines. A supervisor that sends Ctrl+C
or SIGTERM the moment it can find the port therefore hit the operating system's default handling -
no job cancellation, no endpoint cleanup.

The handler now goes in before the start:

- `StopHandle::new()` (`crates/caim/src/server.rs:294`) makes a stop with no server yet, and
  `Server::start_with_stop()` (`crates/caim/src/server.rs:150`) adopts it. `Server::start` is that
  same call with a fresh handle, so nothing that used it before behaves differently.
- `StopHandle::attach()` (`crates/caim/src/server.rs:333`) hands the handle the runner *before* the
  endpoint file is written, and cancels that runner's jobs straight away if a press already arrived.
- `serve` (`crates/caim/src/main.rs:58`) installs the handler first and starts the server with that
  handle. A press during the start raises the stop flag, the accept loop takes no connection, and the
  shutdown still removes the endpoint file with exit 0.
- The new test (`crates/caim/src/server.rs:819`) presses before the start and checks exactly that.

What is left is the window between process start and the first line of `serve`, which is before
anything is published: a signal there cannot strand an endpoint file, because none exists yet.

## Known gaps and follow-ups

- On Windows a **console close** (the X button, logoff, or shutdown) gives the process a few seconds and
  then terminates it whatever happens. `ctrlc` releases its semaphore and returns TRUE, so the clean
  stop starts, but it is not guaranteed to finish inside the grace period. Ctrl+C and Ctrl+Break are not
  time-limited, and those are the cases the prompt asked about.
- A second Ctrl+C can leave `endpoint.json` behind (row 2 above). Deliberate: the user asked to leave,
  and the stale file is the documented case.
