### 1. Routing follows the disk, not the moment the socket was bound (4321260138)

- `Context.offered` was a plain `routing::Offered` built once in `start_with_stop`, so `/v1/tasks` and `submit` answered from a snapshot taken before any install. It is now a `Mutex<routing::Offered>` (`crates/caim/src/server.rs:127`), and `Context::refresh_routing()` (`:158`) recomputes it from the store and hands the matching backend to the queue in the same step.
- `Server::routing()` (`crates/caim/src/server.rs:304`) gives the window a `Routing` handle (`:358`) - an `Arc<Context>` clone, so the window asks the running server to re-read the disk rather than restarting it. `Source` carries it (`crates/caim/src/window/facts.rs:154`) and `Source::refresh_routing()` (`:237`) is what the workers call: after a successful install (`crates/caim/src/window/task.rs:166`), after a repair acknowledgement (`:190`), and after every Remove path including the two failure paths.
- `Runner` gained a `Mutex<Arc<Backend>>` (`crates/caim/src/job.rs:307`) and `set_backend` (`:352`); `fn worker` takes the backend **per job** (`:594`), never holding the lock across a fill. A refresh therefore cannot reach into a job that is already inside a backend, which is what brief rule 2 needs.
- New tests: `a_backend_pointed_at_an_installed_model_serves_the_next_job` and `a_job_already_running_keeps_the_backend_it_took_when_the_backend_is_swapped` (`crates/caim/src/job.rs:1463`, `:1476`), and `a_model_installed_after_the_start_is_offered_once_the_routing_refreshes` (`crates/caim/tests/protocol.rs:402`), which installs into an empty store, refreshes, compares the whole `/v1/tasks` body, then deletes the files and re-reads it.

### 2. A Remove that did not happen is undone (4321260142)

The row goes back to being offered instead of refusing every job until the next restart.

### 3. Cancel reaches a blocked read (4321260151)

- The finding is right: `Cancellable` wrapped the body in a flag checked *between* reads, so a worker parked inside `read` on a stalled connection sat there through a Cancel and kept the window from closing. ureq 3.4 gives a response body no per-read timeout and no way to close it from another thread, so the flag could never have worked.
- `guarded()` (`crates/caim/src/window/task.rs:321`) now puts the connection on a thread of its own (`caim-read`) behind a bounded `sync_channel` (4 x 64 KiB, so a stalled download cannot grow the heap). The download reads the channel with a 100 ms poll, which it can always stop waiting on, so Cancel is seen within a poll interval; 60 s of silence ends the download with a timed-out sentence and the `.part` file keeps what arrived.
- **The honest limit:** the pump thread parked inside a stalled `read` is not interruptible either. It ends when the connection does. What changed is that the *download* and the *window* no longer wait for it - the manager can close while that thread is still parked, which is the brief's rule 4.
- To make the pump legal, `fetch::Stream.reader` widened to `Box<dyn Read + Send>` (`crates/caim/src/fetch.rs:53`, `:59`, `:65`). ureq's `BodyReader` is `Send`: its `BodySourceRef` holds `dyn io::Read + Send + Sync` (`ureq-3.4.2/src/body/mod.rs:973`). ## Independent review round 2 - five findings, all confirmed, all fixed

Codex-cloud's round-2 review of `978f978` came back with five findings: `4321655038` (P1), `4321655044` (P1), `4321655048` (P1), `4321655052` (P2) and `4321655058` (P2). Each was checked against the code before it was changed, and all five are fixed in this round's commit. SPEC amendment 27 is the authorisation for the extra round; independent review, CI and the exact-head FreeBSD runs still have to pass before anything merges, and Codex-Strata neither approves nor merges this PR.

### 1. Two presses could start two workers (4321655038, P1)

- `start()` refused a second task by reading `Work::busy`, which stays empty until a download's first byte arrives, so two presses inside one repaint both passed and two workers ran over the same `.part` file (`crates/caim/src/window/task.rs:98`).
- `Work` now carries an explicit claim: `claim()` takes the window, `release()` gives it back, and a window that is already reporting is refused too (`crates/caim/src/window/facts.rs:75`, `:84`). `start()` claims before the thread exists and releases on both paths that return without a worker.
- `fill()` hands the window back through a `Finished` drop guard (`crates/caim/src/window/task.rs:130`, `:149`) instead of clearing `busy` only on the fall-through path, so a panicking worker cannot leave every button refusing to start anything.
- Tests: `a_second_press_is_refused_before_the_first_worker_has_reported_anything` (`crates/caim/src/window/task.rs:590`) and `a_claimed_window_stays_claimed_until_the_worker_gives_it_back` (`crates/caim/src/window/facts.rs:476`).
- **Not directly testable:** the two-threads-in-one-instant interleaving itself. The tests pin the refusal, the release on the paths that return before a worker starts, and the guard; they do not land in the race window on purpose.

### 2. A failed Check left the model offered (4321655044, P1)

- `fetch::verify` deletes `verified.json` when the size or the hash disagrees (`crates/caim/src/fetch.rs:736`, `:746`), and `verified.json` is the proof `store::is_installed` routes on (`crates/caim/src/store.rs:211`). `check()` marked the row Needs repair and never told the server, so PhotoCraft kept being offered a model this very process had just found broken.
- `check()` works the routing out again after either outcome (`crates/caim/src/window/task.rs:214`): a failure takes the task off the list, a success puts it back.
- Test: `a_failed_check_takes_the_model_off_the_task_list_the_server_answers_with` (`crates/caim/src/window/task.rs:615`) - a scratch store holding a whole, acknowledged lama, `Runner::offered()` ready before the check and not ready after it, with the row marked damaged.

### 3. A model installed after an abandoned Remove stayed unroutable (4321655048, P1)

- A Remove that gave up retired the task, and the retirement was undone only on Remove's own failure paths. A later install called `refresh_routing()` without `restore_task`, so the freshly installed model kept answering with the not-installed sentence until Craft AI Manager restarted.
- Install and both Remove failure paths now go through one helper, `route_installed()` (`crates/caim/src/window/task.rs:191`), which clears the retirement and then re-reads the store.
- Test: `installing_a_model_clears_the_retirement_an_abandoned_remove_left_behind` (`crates/caim/src/window/task.rs:636`) - the submit is refused with 400 while the task is retired and accepted after the helper.

### 4. The task list and the backend were two separate values (4321655052, P2)

- `Context` kept a `Mutex<routing::Offered>` of its own while the queue held a separate backend, and `refresh_routing()` wrote the table first and the backend second. A request landing between those two lines was accepted against a task list the worker had not been pointed at, and its job failed as not ready.
- The two are one value now: `job::Snapshot` (`crates/caim/src/job.rs:274`) holds the offered table and the `Arc<Backend>` together; `Runner::set_routing` (`:380`) replaces both inside one lock, `Runner::offered()` (`:388`) reads them from that same cell, and `Runner::with_routing` (`:344`) lets a start hand its first pair over whole (`crates/caim/src/server.rs:156`). `Context::offered()` (`crates/caim/src/server.rs:145`) is a read of the queue's cell, and `Context` no longer has a table of its own.
- The worker still takes its own copy per job (`crates/caim/src/job.rs:289`), so a refresh cannot reach into a job already inside a backend - the behaviour round 1 established, kept deliberately.
- Test: `the_task_list_and_the_backend_move_as_one_pair` (`crates/caim/src/job.rs:1547`).
- **Not directly testable:** the one-instruction window between the old two writes. The test pins the agreement instead: a start that found nothing advertises nothing and its job fails with the not-ready sentence, and after one `set_routing` the task is advertised and the job accepted against that list runs on the backend that same call installed.

### 5. CUDA progress stopped short when an archive was already on disk (4321655058, P2)

- `fetch::install` returns `AlreadyInstalled` without calling `progress` (`crates/caim/src/fetch.rs:188`), and `Cumulative` banked an archive's bytes only when the *next* report showed a new archive. An archive that never reported was never counted, so on a machine that already had one of the four the bar stopped short of the total the offer showed and the row never read finished.
- `cuda::install` now delegates its loop to `install_components` (`crates/caim/src/cuda.rs:289`), which reports an already-installed archive's own bytes. Extracting the loop is also what makes it testable: the pinned archives carry real NVIDIA hashes, so no test can fetch them end to end.
- `Cumulative::report` (`crates/caim/src/window/task.rs:457`) banks an archive as soon as a report reaches that archive's own size, rather than waiting for the next one.
- Tests: `an_archive_that_is_already_installed_still_reports_its_bytes` (`crates/caim/src/cuda.rs:1049`) - the same fixture installed twice, the second run makes no request and still reports its size; `an_archive_that_is_already_on_disk_still_counts_towards_the_total` (`crates/caim/src/window/task.rs:652`) - today's four pinned sizes with the first archive skipped, reaching exactly 1,915,559,656 of 1,915,559,656.
